# 报警规则模板与联动技术方案

## 1. 背景

当前系统已经具备基础报警能力：

- 支持配置报警规则与多条件阈值判断。
- 无人机执行任务时，`TelemetryStatusMonitor` 会根据实时遥测触发报警。
- 报警触发后会写入 `alert_record`，并在前端报警中心展示。

现阶段存在两个明显短板：

- 报警规则仅支持基础条件配置，缺少“模板 + 规则实例”分层管理能力，难以复用和标准化。
- 报警触发后只记录，不联动任务和通知，无法形成闭环处置。

本次改造目标是在不破坏现有任务、遥测、报警链路的前提下，为系统补齐“报警规则模板配置”和“报警联动”能力。

## 2. 建设目标

### 2.1 功能目标

支持以下能力：

- 支持将告警配置拆分为“规则模板”和“普通规则”两层。
- 规则模板可作为标准规则沉淀和复用，普通规则继承模板后用于任务实际绑定。
- 报警触发后支持联动动作：
  - 自动中断任务
  - 发送通知
- 通知能力先预留统一扩展接口，默认实现先记录日志并回写执行结果，后续可接入第三方短信 SDK。
- 前端支持模板配置、普通规则配置、联动动作和通知参数配置。
- 报警记录可查看本次联动是否执行、执行结果如何。

### 2.2 非功能目标

- 与现有 `MissionService.interrupt()` 复用，不重复发明任务中断流程。
- 避免重复触发同一条未处理报警时反复执行联动。
- 兼容现有数据库，采用启动期安全补字段方式平滑升级。

## 3. 现状分析

### 3.1 当前告警规则模型

当前 `alert_rule` 仅包含：

- `name`
- `description`
- `logic_operator`

当前 `alert_rule_condition` 包含：

- `metric_code`
- `comparator`
- `threshold`

这说明规则只覆盖“判断条件”，没有覆盖“规则模板元信息”和“联动动作配置”。

### 3.2 当前告警触发流程

当前流程如下：

1. `TelemetryStatusMonitor` 每秒轮询 Redis 中的无人机遥测。
2. 当无人机状态为 `EXECUTING` 且携带 `missionId` 时，进入 `evaluateAlerts()`。
3. 根据任务绑定的 `ruleId` 加载规则与条件。
4. 命中规则后写入 `alert_record`。
5. 前端报警中心仅展示记录，由人工处理。

### 3.3 当前问题

- 缺少模板属性，无法区分“标准规则模板”和“普通规则实例”。
- 缺少联动配置，无法表达“命中后要不要中断任务、要不要通知”。
- 缺少联动执行结果记录，无法追踪动作是否成功。
- 通知能力没有统一抽象，后续接短信 SDK 时需要侵入式改造。

## 4. 总体设计

### 4.1 设计原则

- 规则与动作放在同一配置对象中，降低管理成本。
- 联动执行只在“新报警记录创建成功”时触发一次。
- 自动中断复用现有任务中断接口。
- 通知通过接口抽象，默认提供占位实现。

### 4.2 修订说明（模板与规则分离）

根据最新业务约束，报警模板与报警规则需要拆分：

- 报警模板负责沉淀基础配置，包含条件、联动动作和通知基础参数。
- 普通报警规则是任务实际绑定的规则实例，可选择继承某个模板。
- 模板与普通规则在前端告警中心中以两种模式分开展示和维护。
- 模板支持新增、编辑和删除，但删除时需要校验是否已被普通规则引用。
- 普通规则创建时可选择模板，并在模板基础上继续补充或覆盖自身规则。
- 任务创建时只能选择普通规则，不能直接绑定模板。

### 4.3 数据模型扩展

#### 4.2.1 `alert_rule` 新增字段

- `template_enabled`：是否作为模板发布。
- `template_id`：普通规则继承的模板主键。
- `template_code`：模板编码，便于标准化引用。
- `template_category`：模板分类，如飞行安全、设备健康、环境异常。
- `auto_interrupt`：报警后是否自动中断任务。
- `notify_enabled`：是否发送通知。
- `notify_channels`：通知渠道，先用逗号分隔字符串保存，如 `SMS`。
- `notify_targets`：通知目标，先保存手机号或接收人标识列表。
- `notify_template`：通知内容模板。

#### 4.2.2 `alert_record` 新增字段

- `linkage_status`：联动执行状态，取值建议为 `PENDING`、`SUCCESS`、`PARTIAL`、`FAILED`、`SKIPPED`。
- `linkage_summary`：联动执行摘要，用于展示“任务已中断”“短信待接 SDK”等结果。
- `notification_status`：通知执行状态，便于区分中断成功但通知未发出的场景。

### 4.4 模块划分

#### 4.3.1 `AlertSchemaInitializer`

职责：

- 启动时检查 `alert_rule` 和 `alert_record` 是否缺少新增字段。
- 如果缺失则执行 `ALTER TABLE ... ADD COLUMN ...`。
- 保障已有库平滑升级，不依赖重新导入 SQL。

#### 4.3.2 `AlertLinkageService`

职责：

- 在告警记录创建后执行联动动作。
- 管理自动中断和通知发送的组合结果。
- 回写 `alert_record` 的联动执行结果。

#### 4.3.3 `AlertNotificationSender`

职责：

- 提供统一通知发送接口。
- 当前默认实现为日志/占位实现。
- 后续可替换成短信 SDK 实现，而不改动告警主流程。

## 5. 核心流程设计

### 5.1 模板配置流程

1. 用户在前端告警中心右上角切换到“模板配置”模式。
2. 在模板模式下支持新增、编辑和删除模板。
3. 模板定义基础能力：
   - 模板名称
   - 模板编码和分类
   - 条件逻辑与阈值条件
   - 是否自动中断任务
   - 是否发送通知
   - 通知渠道、接收人、通知模板
4. 模板保存后作为普通规则的基础配置来源。

### 5.2 普通规则创建流程

1. 用户在前端告警中心右上角切换到“普通规则配置”模式。
2. 用户创建或编辑普通规则。
3. 可选选择某个模板作为基础配置来源。
4. 选择模板后，前端将模板基础配置带入普通规则表单。
5. 用户可继续修改普通规则自己的名称、描述、条件和联动参数。
6. 前端调用 `/api/alerts/rules` 创建或更新普通规则，模板通过 `templateId` 关联。
7. 后端保存普通规则，并保留模板引用关系。

### 5.3 报警触发与联动流程

1. `TelemetryStatusMonitor` 发现执行中任务的遥测数据。
2. 命中规则后先检查是否已存在同规则、同任务、未处理报警。
3. 若不存在，则创建新的 `alert_record`。
4. 新记录创建后调用 `AlertLinkageService.execute(...)`。
5. `AlertLinkageService` 根据规则配置执行：
   - 自动中断任务：调用 `MissionService.interrupt(missionCode)`
   - 发送通知：调用 `AlertNotificationSender.send(...)`
6. 将执行结果回写到 `alert_record`。

### 5.4 重复触发控制

当前系统已经用“同规则 + 同任务 + 未处理”去重，本次继续沿用。

这样可以保证：

- 同一告警未处理期间不会不断新增记录。
- 联动动作也不会在短时间内被重复执行。

## 6. 联动算法与状态策略

### 6.1 自动中断策略

满足以下条件时执行自动中断：

- 规则命中
- `auto_interrupt = true`
- 当前任务存在且任务状态允许中断

中断动作说明：

- 优先复用 `MissionService.interrupt(missionCode)`。
- 任务状态切换为 `INTERRUPTED`。
- 已绑定无人机会收到中断命令。

### 6.2 通知策略

满足以下条件时执行通知：

- 规则命中
- `notify_enabled = true`

通知当前先做两层设计：

- 抽象层：`AlertNotificationSender`
- 默认实现：`LoggingAlertNotificationSender`

默认实现行为：

- 生成通知内容
- 记录日志
- 返回“已进入占位发送流程”的结果

后续接短信 SDK 时，只需要新增具体实现，例如 `SmsAlertNotificationSender`。

### 6.3 联动结果判定

- 仅中断成功：`SUCCESS`
- 仅通知成功：`SUCCESS`
- 中断成功但通知失败：`PARTIAL`
- 中断失败且通知失败：`FAILED`
- 未配置联动动作：`SKIPPED`

`linkage_summary` 用于记录更易读的结果摘要，便于前端展示。

## 7. 后端改造方案

### 7.1 实体与 DTO 改造

改造以下对象：

- `AlertRule`
- `AlertRecord`
- `AlertRuleCreateRequest`
- `AlertRuleDto`
- `AlertRecordDto`

补充说明：

- 新增 `templateId/templateName` 字段，明确普通规则与模板的继承关系。
- 当前前端统一通过 `/api/alerts/rules` 获取完整配置列表，再按 `templateEnabled` 拆分为模板和普通规则两种模式展示。
- 任务创建接口在后端额外校验：若传入模板规则 ID，则直接拒绝创建。

### 7.2 服务层改造

`AlertService` 需要补齐：

- 模板与普通规则两类配置的新字段保存与返回
- 普通规则创建时的模板继承逻辑
- 模板删除时的引用校验
- 规则列表中模板、继承关系与联动信息展示

### 7.3 监控触发点改造

`TelemetryStatusMonitor.evaluateAlerts()` 调整为：

1. 创建 `AlertRecord`
2. 调用 `AlertLinkageService`
3. 回写联动结果

### 7.4 通知扩展点

新增接口：

- `AlertNotificationSender`

新增默认实现：

- `LoggingAlertNotificationSender`

入参建议包含：

- 规则信息
- 告警记录
- 任务信息
- 命中的条件
- 当前无人机编号

## 8. 前端改造方案

### 8.1 告警中心界面分层

在 `AlertsCenter` 中保留统一的“告警配置”区域，并在卡片右上角增加模式切换：

- 模板配置模式：管理模板列表与模板新增入口
- 普通规则配置模式：管理普通规则列表与普通规则新增入口

右侧区域随模式切换显示不同内容：

- 模板模式显示模板说明与使用约束
- 普通规则模式显示报警记录与未处理状态

### 8.2 模板与普通规则表单扩展

模板表单新增配置项：

- 模板编码
- 模板分类
- 自动中断开关
- 通知开关
- 通知渠道
- 通知目标
- 通知模板
- 条件配置

普通规则表单新增配置项：

- 模板选择
- 自动中断开关
- 通知开关
- 通知渠道
- 通知目标
- 通知模板
- 条件配置

### 8.3 告警规则卡片展示

普通规则卡片增加以下信息：

- 来源模板
- 联动动作标签

模板卡片展示以下信息：

- 模板编码
- 模板分类
- 基础联动动作

### 8.4 告警记录展示

记录表格增加：

- 联动状态
- 联动摘要
- 通知状态

## 9. 验证方案

### 9.1 功能验证

验证场景一：模板配置

- 在“模板配置”模式下创建一条模板规则
- 确认模板列表能正确显示模板标识、模板编码、模板分类和联动配置

验证场景二：普通规则继承模板

- 在“普通规则配置”模式下创建一条普通规则，并选择已有模板
- 确认模板条件和联动参数能自动带入普通规则表单
- 保存后确认规则列表展示继承来源标签

验证场景三：自动中断

- 创建带 `auto_interrupt = true` 的规则
- 给任务绑定规则
- 触发告警
- 验证任务状态变成 `INTERRUPTED`

验证场景四：任务绑定约束

- 在任务创建页面确认仅能选择普通规则
- 手工调用后端接口传入模板规则 ID
- 验证接口返回拒绝信息

验证场景五：通知占位

- 创建带 `notify_enabled = true` 的规则
- 触发告警
- 验证 `alert_record` 中写入通知状态和联动摘要
- 验证后端日志出现通知占位发送记录

### 9.2 回归验证

- 旧规则不配置新增字段时，仍然可正常触发报警记录。
- 未配置联动时，不影响现有报警中心的基本展示和处理。
- 模板与普通规则分开展示后，不影响既有普通规则的读取和使用。

## 10. 后续演进建议

- 为模板增加版本管理和发布状态，支持模板升级与规则实例平滑迁移。
- 将 `notify_channels` 从字符串演进为 JSON 结构，支持多渠道并发。
- 接入真实短信/企业微信/邮件网关后，新增发送回执与重试机制。
- 增加联动动作审计表，记录每一步执行耗时和失败原因。
