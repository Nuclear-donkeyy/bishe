# 任务综合调度优化技术方案

## 1. 背景与目标

当前系统已经具备基础的任务创建、任务入队、MQTT 下发和基于遥测状态回写任务状态的闭环能力，但调度策略仍然偏“静态分配”：

1. 任务创建时由前端手工指定候选无人机。
2. 后端将任务写入 Redis 队列。
3. `MissionQueueService` 周期性扫描队列，按 `priority` 排序。
4. 每个任务只要找到一架“在线且未被运行中任务占用”的无人机，就直接下发 `mission.start`。
5. 当遥测上报 `EXECUTING/RUNNING` 时，将任务置为 `RUNNING`；当上报 `RETURNING/IDLE` 时，将任务置为 `COMPLETED`。

这套机制可以跑通演示流程，但还存在几个明显短板：

1. 只看静态优先级，不看无人机实时状态。
2. 不考虑任务时长，长任务和短任务抢占同一类资源时决策粗糙。
3. 不考虑电量和续航，可能把高成本任务派给即将返航的设备。
4. 不考虑设备健康度，链路抖动或关键指标异常时仍可能被选中。
5. 不支持抢占，高优先级任务只能等待低优先级任务自然结束。
6. 不支持动态调整，运行中的任务在电量急降、链路恶化时无法自动回收并重排。

本次优化目标如下：

1. 在不破坏现有前后端基础交互的前提下，引入综合调度算法。
2. 调度因子覆盖：电量、任务时长、优先级、设备健康度。
3. 支持未手工指定无人机时的自动选机。
4. 支持高优先级任务对低优先级运行任务进行抢占。
5. 支持运行期动态调整，能够因健康度/电量变化触发重排。
6. 保留现有 MQTT 下发与遥测回写机制，尽量降低改造范围。

## 2. 当前调度流程理解

### 2.1 创建阶段

`MissionService.create()` 当前流程：

1. 创建 `Mission`，初始状态写为 `QUEUE`。
2. 保存航线点 `mission_route_points`。
3. 保存任务与候选无人机关系 `mission_uav_assignments`。
4. 若存在候选无人机，则调用 `MissionQueueService.enqueue()` 写入 Redis。

### 2.2 排队阶段

`MissionQueueService.enqueue()` 当前只保存以下信息：

1. `missionCode`
2. `uavCodes`
3. `route`
4. `priority`
5. `enqueuedAt`
6. `dispatchedAt`

因此队列项缺少用于智能调度的关键上下文，例如：

1. 预计任务时长
2. 航线距离
3. 所需最低电量
4. 是否允许抢占
5. 当前是否因健康度问题被阻塞
6. 已被抢占次数

### 2.3 调度阶段

`MissionQueueService.processQueue()` 当前逻辑：

1. 从 Redis 扫描全部排队任务。
2. 按 `priority` 和 `enqueuedAt` 排序。
3. 对每个任务，从候选无人机里找一架 `isUavReady()` 为真的设备。
4. 直接下发 `mission.start`。

`isUavReady()` 目前只做三件事：

1. 设备存在。
2. Redis 里有遥测数据。
3. 关联任务里没有 `RUNNING` 状态的任务。

这个判定过于粗糙，在线不等于可执行。

### 2.4 状态回写阶段

`TelemetryStatusMonitor` 读取 Redis 遥测：

1. 如果 `status=EXECUTING/RUNNING`，任务置为 `RUNNING`。
2. 如果 `status=RETURNING/IDLE`，任务置为 `COMPLETED`。
3. `EXECUTING` 时同时进行告警计算和任务数据聚合。

该机制已经形成了“下发-执行-完成”的最小闭环，是本次优化要保留的基础。

## 3. 优化后的总体流程

优化后的流程改为“任务画像 + 设备画像 + 综合评分 + 抢占决策 + 动态重排”：

1. 任务创建时构建任务画像：
   - 航线距离
   - 预计任务时长
   - 预计电量消耗
   - 调度优先级
   - 是否允许抢占

2. 调度周期内构建设备画像：
   - 在线状态
   - 电量
   - 估算剩余航程/续航
   - 链路质量
   - 遥测完整度
   - 当前任务占用情况
   - 设备健康度评分

3. 对“任务-设备”组合计算综合得分。

4. 优先尝试把任务分配给空闲且高分设备。

5. 若没有可用空闲设备，则进入抢占决策：
   - 仅高优先级任务可抢占低优先级运行任务；
   - 被抢占任务必须满足“允许回队、进度未过深、近期未重复抢占”等条件；
   - 被抢占任务会回到队列，状态改为 `PREEMPTED`。

6. 运行中的任务持续接受动态检查：
   - 电量低于安全阈值；
   - 健康度跌破阈值；
   - 链路异常、关键数据缺失；
   - 触发后自动中止当前执行并重排。

## 4. 调度算法设计

### 4.1 任务画像

对每个任务构造如下字段：

1. `routeDistanceKm`
   - 根据航线点计算总里程。
2. `estimatedDurationMinutes`
   - 使用默认巡航速度估算。
3. `requiredBatteryPercent`
   - 基于时长消耗和安全返航余量估算。
4. `priorityScore`
   - `HIGH=100`，`MEDIUM=60`，`LOW=30`。
5. `agingScore`
   - 排队越久，得分越高，避免低优先级任务永久饿死。
6. `preemptible`
   - 允许被抢占并重新排队。

建议公式：

`requiredBatteryPercent = max(20, estimatedDurationMinutes * 2.5 + 15)`

说明：

1. `2.5` 表示每分钟理论消耗系数。
2. `15` 代表返航与安全余量。
3. `20` 作为最低安全门槛。

### 4.2 设备画像

从遥测中提取：

1. `batteryPercent`
2. `status`
3. `missionId`
4. `linkQuality`
5. `rangeKm`
6. `lat/lng`
7. 遥测数据完整度

设备健康度评分 `healthScore` 按 100 分制计算：

1. 基础在线分：30
2. 电量质量分：最多 30
3. 链路质量分：最多 25
4. 遥测完整度分：最多 15

建议规则：

1. 无遥测或状态离线：0 分
2. 电量 ≥ 80：30 分；50~79：20 分；30~49：10 分；<30：0 分
3. `linkQuality` 存在时按比例折算；缺失但其他数据完整时给中性分
4. 位置、电量、状态齐全则给完整度满分

### 4.3 任务-设备综合评分

对每个候选组合计算：

`totalScore = missionPriorityScore * 0.35 + agingScore * 0.10 + batteryFitness * 0.25 + healthScore * 0.20 + durationFitness * 0.10 - preemptionPenalty`

说明：

1. `batteryFitness`
   - 当前电量减去任务所需电量后的富余度折算。
2. `durationFitness`
   - 对短任务给轻微优待，提升系统吞吐。
3. `preemptionPenalty`
   - 当设备当前正承载运行中任务时施加惩罚。

准入条件先于评分：

1. 设备必须在线。
2. 电量必须高于 `requiredBatteryPercent`。
3. 健康度必须高于最低阈值，例如 45 分。
4. 若设备正在运行高于或等于当前任务优先级的任务，不允许抢占。

### 4.4 抢占规则

抢占只在以下情况下允许发生：

1. 当前待调度任务优先级为 `HIGH`。
2. 没有可用空闲设备。
3. 存在运行中的较低优先级任务占用了可行设备。
4. 被抢占任务当前进度低于 80%。
5. 被抢占任务近期未频繁被抢占。

抢占流程：

1. 选中最适合的被占用设备。
2. 向该无人机发送 `interrupt` 指令。
3. 将被抢占任务状态改为 `PREEMPTED`。
4. 将被抢占任务重新入队，保留航线与优先级。
5. 等无人机遥测回到 `IDLE` 后，再调度高优任务。

### 4.5 动态调整规则

对所有 `RUNNING` 任务周期性评估：

1. 若 `batteryPercent < dynamicBatteryFloor`，触发重排。
2. 若 `healthScore < dynamicHealthFloor`，触发重排。
3. 若链路状态持续异常，触发重排。

动态重排处理：

1. 下发 `interrupt`。
2. 任务置为 `PREEMPTED`。
3. 清理当前执行态，重新回到调度队列。

## 5. 代码改造方案

### 5.1 后端核心改造

#### 5.1.1 `MissionQueueService`

从“简单队列派发器”升级为“综合调度器”，新增能力：

1. 任务画像构建。
2. 设备遥测快照解析。
3. 综合评分计算。
4. 空闲设备调度。
5. 抢占决策。
6. 动态重排。
7. 事件记录。

#### 5.1.2 队列项扩展

`MissionQueueItem` 增加：

1. `routeDistanceKm`
2. `estimatedDurationMinutes`
3. `requiredBatteryPercent`
4. `preemptedCount`
5. `lastPreemptedAt`
6. `candidateUavCodes`
7. `lastSchedulingReason`

#### 5.1.3 任务状态扩展

在 `MissionStatus` 中新增：

1. `PREEMPTED`

语义：

1. `QUEUE`：等待首次调度。
2. `RUNNING`：已开始执行。
3. `PREEMPTED`：执行中被调度器回收，等待再次调度。
4. `COMPLETED`：任务完成。
5. `INTERRUPTED`：人工中断或不可恢复中断。

#### 5.1.4 任务事件

引入 `MissionEventMapper`，写入 `mission_events`：

1. `MISSION_ENQUEUED`
2. `MISSION_DISPATCHED`
3. `MISSION_PREEMPTED`
4. `MISSION_REQUEUED`
5. `MISSION_DYNAMIC_REBALANCED`
6. `MISSION_COMPLETED`

用于调试、验证和论文描述。

#### 5.1.5 自动选机

若任务创建时未指定 `assignedUavs`：

1. 调度器自动从全部设备中筛选候选集。
2. 首次派发成功时再写入 `mission_uav_assignments`。

### 5.2 前端兼容性

现有前端不需要大改即可继续使用，但建议补充：

1. 任务状态标签支持 `PREEMPTED`。
2. 任务筛选下拉支持 `PREEMPTED`。
3. 详情页显示最近调度事件。

本轮至少完成状态标签兼容，避免页面看到新状态时落入默认分支。

## 6. 验证方案

### 6.1 单体逻辑验证

验证点：

1. 高电量、高健康度设备优先于低电量设备。
2. 相同优先级下，等待时间更长的任务最终能被调度。
3. 高优任务到来时，低优运行任务会被抢占。
4. 运行中任务电量过低会被动态回收并重排。

### 6.2 集成验证

基于现有 Docker 环境：

1. 启动 MySQL、Redis、MQTT、后端、前端。
2. 注册至少两架无人机。
3. 注入不同电量/链路质量的遥测。
4. 创建一组不同优先级、不同航线长度的任务。
5. 验证调度结果与预期一致。
6. 在运行期间人为降低某架无人机电量，验证动态重排。

### 6.3 验证输出

需要最终给出：

1. 任务状态变化结果。
2. 调度决策日志。
3. `mission_events` 记录。
4. API 返回结果和关键截图/命令输出摘要。

## 7. 预期收益

改造完成后，系统将从“静态优先级派发”升级为“面向实时资源状态的综合调度系统”，主要收益如下：

1. 任务分配更符合无人机实时能力。
2. 高优先级任务响应更快。
3. 低电量与异常链路情况下的误派发显著减少。
4. 支持抢占和动态重排，更接近真实调度系统。
5. 方案结构清晰、工程改造点集中，适合论文和答辩展示。
